# Repro: Risks

Revision 2 (2026-11-17): $0 budget. New section D covers the free-tier risks; several earlier rows changed because there is no paid model and no rented VM.

What can go wrong, how likely, how bad, and what the plan does about it. Ordered by how much damage each could do to the project's claims.

L = likelihood, I = impact (H / M / L).

## A. Risks to the validity of the numbers

| # | Risk | L | I | What the plan does | How we would notice |
|---|---|---|---|---|---|
| R1 | **The fix leaks to the agent.** Paths: sealed dataset fields in a prompt, later issue comments (`hints_text`), names of the failing tests, future commits reachable in `.git`, network access, a newer copy of the library in site-packages. Free providers may also keep prompts, so a leak would be stored somewhere I do not control. | M | H | `AgentView` vs `SealedView` types. `.git` replaced with a single commit. `--network none`. Loader never passes `hints_text` or fail-to-pass names. | Canary scan over every prompt and trace for fix hunks, gold test bodies, and test names (T6.6, V9.3). T6.D6 checks git history inside the container. |
| R2 | **Training-data contamination.** SWE-bench repos, fixes, and tests are public and old. The model may have memorised the gold tests. Absolute S is inflated for every system on this benchmark. | H | M | State it in the README. Lean on the paired comparison (agent vs single prompt, same model, same contamination). Report the memorisation check: similarity of each generated test to the gold test, and S with high-similarity cases removed. | Share of generated tests above 0.8 similarity to gold. |
| R3 | **Tuning on the test set.** Prompt and gate changes made after seeing Test results would make the headline number meaningless. | M | H | Dev and Test lists committed before any model run on Test. Freeze tag. `repro eval` refuses Test runs off a freeze tag (T7.3) and refuses Test instances in dev configs (T7.4). | Git history: pre-registration commit and freeze tag predate result files. |
| R4 | **My harness disagrees with the official one.** Different images, different test selection, different outcome parsing. | M | H | Official SWT-bench harness used wherever it fits on a free runner. Reuse `swebench` test specs and parsers. Gold agreement on 10 pilots before anything else, then on all Test instances. | Harness agreement rate and the list of disagreements (target at least 95%). |
| R5 | **Sample too small to support the claim.** 50 instances gives about ±13 points. The smallest agent-vs-baseline result that reaches p < 0.05 is about 10 wins to 2 (a 16-point net gap). A real but smaller gain will likely read as "not significant". | H | M | Wilson CIs on everything, including gate precision. Paired exact McNemar. Variance reruns on all 50. The README states what N=50 can and cannot show (EVAL H1) and never claims a difference the test does not support. | CI width and p-value in the report. |
| R6 | **Unfair comparison to published results.** Different model (free tier vs frontier), sample vs full set, self-run vs verified, unit-test vs script mode. | H | M | Comparison table in EVAL section 7 says exactly what is and is not comparable. README never states or implies a rank. | Review checklist in M10. |
| R7 | **The gate rejects correct tests or passes wrong ones more than expected.** | H | M | This is a measured quantity, not a defect to hide: gate precision, recall cost, per-check rejection counts. Tune rules on Dev only. LLM judge as a measured ablation. | H3 numbers; hand-labelled gate misses in the failure notes. |
| R8 | **Flaky environments blamed on Repro (or the reverse).** Some benchmark instances are unstable on their own. Shared Actions runners add timing noise. | M | M | SWT-bench already filters unreliable instances. Gold tests get the same 10x audit as a control. | Gold-test flaky rows in `audit.jsonl`. |
| R9 | **Mutation score misread.** Equivalent mutants cannot be killed; a low raw score may mean nothing. Old Python syntax may break mutant generation. At N=50 the score rests on only about 15 to 25 instances. | M | M | Always report next to the gold tests' score on the same mutants, with a bootstrap CI. Scope to fix-changed lines. Discard mutants that do not compile. State the caveat beside the number. | `score_gold` well below 100% signals equivalent mutants. |
| R10 | **Model nondeterminism and version drift.** Reruns differ; free-tier models get updated, renamed, or retired without notice. | H | M | Pin exact model version strings; refuse `-latest` in eval configs. Record the model ID in every row. Variance reruns. Cassettes and full traces committed so results can be re-scored without the API. Restart rule in EVAL section 5 if the model disappears mid-run. | Spread across the 3 reruns; `live-smoke.yml` model list changes. |
| R11 | **Mixed models contaminate the comparison.** Automatic failover could quietly serve part of a run from a different model, making agent vs baseline an unpaired comparison. | M | H | `pinned` policy for every headline config: failover only to routes serving the same weights, otherwise defer. `chain` only for dev and demo. Every call records its route; every row has `mixed`. | Model purity check (EVAL section 6, T3.18, V9.8). |

## B. Risks to getting it built

| # | Risk | L | I | What the plan does | How we would notice |
|---|---|---|---|---|---|
| R12 | **The benchmark does not fit on a free runner.** Actions runners have 14 GB of SSD, 16 GB RAM, and 6-hour jobs. The SWT-bench harness recommends about 120 GB for the full set and builds images itself. | M | H | Free preinstalled tools at job start to reclaim disk (commonly 20 to 30 GB). One instance in flight per container slot; remove its image after. Prefer prebuilt SWE-bench instance images from Docker Hub over building. Official scoring runs one instance per matrix job. If the official harness still cannot build some instances, they are listed and the headline uses my oracle (MILESTONES cut item 6). | E0 `box-notes.md` (disk before and after); E1 failures. |
| R13 | **Build sessions cannot run Docker or reach the models or dataset.** Checked 2026-11-16: the chat workspace has no Docker daemon and no access to Docker Hub, GHCR, or Hugging Face. | Certain | H | `Sandbox`, `ChatModel`, `InstanceSource`, `Clock` interfaces with fakes; fixture repos; cassettes; contract tests that run on both backends; all real runs in Actions, which a chat session can trigger. | Already known. |
| R14 | **Fakes drift from real behaviour.** Tests pass in chat, things break in Actions. `FakeProvider` may not match how real providers fail. | M | M | Contract tests are one suite run against `LocalSandbox` and `DockerSandbox`. Error classifier is tested on recorded real error bodies from `live-smoke.yml`. Cassettes from real runs replace scripted `FakeLLM` scenarios as soon as they exist (M5). First real run is 10 pilots. | E1 and live-smoke failures. |
| R15 | **Non-pytest test runners.** Django is a large share of Verified and uses its own runner; sympy too. Test placement rules differ per repo. | H | M | Reuse `swebench` commands and log parsers (T6.5). Agent prompt tells it to copy the nearest existing test's style and location. `check` returns clear "not collected" feedback. | "Placement or runner problem" count in failure notes. |
| R16 | **Fix needs a rebuild** (compiled extensions) so "apply patch, run test" gives wrong results. | L | M | Oracle follows the `swebench` eval steps for the instance, including reinstall where the spec says so. Gold agreement check covers it. | Gold test not F→P on that instance. |
| R17 | **Scope creep.** Eleven milestones plus Actions runs, on top of two internships and two other projects. The free-tier router adds work to M3. | H | M | One milestone per session, explicit "not in this milestone" lists, B1 allowed to slip from M3 to M4, a fixed cut order in MILESTONES.md, and a not-cuttable list. | A milestone needing a third session. |
| R18 | **Chat workspace does not persist.** Anything not pushed is lost. | H | M | Every session ends with a push. Session kickoff prompt starts with a clone. Decisions go in `DECISIONS.md` in the repo. Results live on the `results` branch, not in any workspace. | Missing work at the next clone. |
| R19 | **The free model is too weak.** It may not clear the floor, or may follow the action protocol poorly. | M | M | Decision rule set in advance (EVAL section 5): below 3 of 15 on Dev after two rounds, move to the next free model. A low S on a free model is still a reported result; gate precision and the harness stand on their own. | Dev S; parse-error counts in traces. |

## C. Safety

| # | Risk | L | I | What the plan does | How we would notice |
|---|---|---|---|---|---|
| R20 | **Untrusted code escapes the sandbox.** Repo code and model-written commands run on the runner. | L | H | Docker with no network, dropped capabilities, no host mounts, no Docker socket, resource limits, on an ephemeral Actions VM destroyed after each job. Never `LocalSandbox` for anything but fixtures. Documented limit: not safe against kernel-level container escapes; a public GitHub App would need gVisor or Firecracker. | T6.D2 to T6.D5. |
| R21 | **API key leak.** Key pasted in a chat, committed, written to a trace, or exposed to a fork's pull request once the repo is public. | M | H | Keys only in Actions secrets, entered with `gh secret set` prompts, never pasted into a chat. Never inside a container (T6.D9). Never in artefacts (T3.14). Workflows never trigger on `pull_request_target`, and forks never get secrets (T6.10). CI check for key-shaped strings. Rotate any key in doubt; all are free to reissue. | CI secret check; provider dashboards showing unexpected usage. |
| R22 | **Prompt injection through issue text or repo files.** "Ignore your instructions and..." | M | L (v1), H (v2) | In v1 the agent has no network, no secrets, and can only emit additions to test files, so the worst case is wasted tokens or a wrong test, both bounded. Tested in T5.17. For the v2 GitHub App: issue text is treated as data, never interpolated into shell commands (T11.3), and it comments only when the gate passes. | Traces with unusual tool use. |
| R23 | **Leaked containers or a full disk on the runner.** | M | M | Label-based reaper at start and exit (T6.3, T6.D7). Image removal and `docker system prune` after each instance. Disk usage logged per unit. | Disk usage creeping up within a job. |

## D. Free-tier risks (new in revision 2)

| # | Risk | L | I | What the plan does | How we would notice |
|---|---|---|---|---|---|
| R24 | **A free tier is cut or removed without notice.** This has happened: reports describe Gemini's free Flash quota dropping to about 20 requests per day. Cerebras already has no standing free tier. | H | H | Limits live in `routes.yaml` and are checked at runtime, not hard-coded. Mistral alone covers the plan with about 92% of a month's tokens to spare. Runs are resumable, so a bad night costs nothing. Restart rule if the primary model's tier disappears mid-run (EVAL section 5). `verified_on` dates and `live-smoke.yml` catch changes before a run. | `live-smoke.yml` output; quota-exhausted errors far earlier than the configured limits. |
| R25 | **Rate limits slow runs enough to distort results.** If waits counted against the agent's wall clock, a congested provider would lower S. Also: nights go by and the run never finishes. | M | M | The 25-minute wall-clock budget counts active time only; rate-limit waits are excluded, with a separate 60-minute hard cap including waits. `rate_limit_wait_s` is recorded per unit. Static 1/N quota split across 6 shards keeps parallel jobs under the shared limit. `repro status` estimates nights left. | Rate-limit wait share in the report; units stopped by the hard cap. |
| R26 | **"OpenAI-compatible" is not identical everywhere.** Field names, system-role support, stop sequences, error bodies, and tool-calling behaviour differ between providers. | H | M | Text action protocol instead of native tool calling. Per-route capability flags. Error classifier tested against recorded bodies from each provider. `live-smoke.yml` checks every route before a run. | Live-smoke failures; parse-error spikes on one route. |
| R27 | **Free tiers may train on prompts, and have usage terms.** Mistral's and Google's free tiers may use prompts to improve their models. Free tiers are meant for evaluation and prototyping. | Certain | M (v1), H (v2) | v1 only sends public open-source code and public issue text, and nothing sealed (R1). This is research and evaluation use. One account per provider: never create extra accounts to multiply free quota, which breaks provider terms and risks a ban. For private code (v2), routes marked `trains_on_data` are refused by a `private_code` flag (DESIGN section 9). | Config review; the `private_code` flag test in v2. |
| R28 | **Docker Hub pull limits.** Anonymous pulls are rate-limited per IP, and Actions runners share IPs. | M | M | Log in with a free Docker Hub account (higher limit). Pull each instance image once per job. Back off and retry on 429 from the registry. | Registry 429s in job logs. |
| R29 | **GitHub Actions limits and behaviour.** The volume needs a public repo (or a cut eval). Jobs stop at 6 hours. Scheduled workflows can be delayed at busy times and are disabled after 60 days without repo activity. | M | M | Make the repo public before M6 (my decision). 330-minute deadline inside the 6-hour limit, with a commit per finished unit. Every scheduled run can also be started by hand. The schedule only acts while `eval/active_run.yaml` exists. | Missed nightly runs; `repro status` not moving. |
| R30 | **Accidental paid usage.** A key from an account that has billing enabled could quietly start charging, for example a Google Cloud project with billing on. | L | M | No card on any provider account. AI Studio key from a project without billing. Eval configs only accept routes marked `free: true` in `routes.yaml`. The ledger prints the list-price equivalent, so a paid route would also be noticed as non-zero actual spend. | Any charge notification; a route without `free: true` in an eval config fails validation (T3.23). |

## E. Positioning

| # | Risk | L | I | What the plan does |
|---|---|---|---|---|
| R31 | **"Why not just use Claude Code? It already scores 88%."** | Certain | M | Agree, then answer: the model is not the contribution, the harness is. Repro reports what the leaderboard does not: precision of "reproduced" with no fix available, tokens per bug, flaky rate, mutation score against human tests. It does so at $0 on a free model, and I can explain every line and every number. `docs/DEFENSE.md` in M10 holds the prepared answers. |
| R32 | **The headline number looks low next to the leaderboard**, more so on a free model. | H | M | Lead with the trio (S, gate precision, tokens per bug at $0), not S alone. Place S against the older paid-model band (14% to 28%) as well as the frontier band. Show the token-ceiling curve. |
| R33 | **Results are disappointing** (agent barely beats the single prompt, or N=50 cannot separate them). | M | M | That is still a result. The plan requires failure notes and a per-check breakdown, so the write-up explains why. Do not tune after the fact to rescue it. |
| R34 | **Real repos are much harder than the benchmark** because no one has built the environment. | Certain | M | Say so. v1 needs `.repro.yml` with an image and a test command. M10 documents one real-repo run including the setup effort. v2 design reuses the repo's CI environment. |
| R35 | **Free-tier results are hard for anyone to reproduce later**, because the free models and limits will have changed. | H | L | Commit traces, cassettes, exact model IDs, `routes.yaml` with dates, and the frozen config. Anyone can re-score the committed candidates without calling a model. |

## Things explicitly not defended against

- Container-escape exploits (R20).
- A provider changing behaviour under a fixed model ID.
- Benchmark label errors in SWT-bench Verified itself (counted against Repro like any other failure).
- Low-rate flakiness below what 10 reruns can detect (EVAL H4 power table).
- A free tier vanishing entirely during the project with no replacement (the project then reports whatever finished, on one model, and says so).
