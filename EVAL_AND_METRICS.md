# Repro: Eval and Metrics

Revision 2 (2026-11-17): $0 budget. The headline set is now 50 bugs, models are free-tier, cost is measured in tokens, and runs happen in resumable overnight batches.

The eval is built before the agent. Milestones M1 to M4 produce the full measuring pipeline on toy bugs; the agent arrives in M5 and is measured from its first run.

Rule for this doc: every number that will appear in the README has a definition, a denominator, and a procedure here. If it is not defined here, it does not go in the README.

## 1. Headline numbers

| ID | Number | One-line definition |
|---|---|---|
| H1 | Success rate S | Share of bugs where Repro's test fails before the real fix and passes after |
| H2 | Compute per bug | Tokens and requests per bug attempted and per bug reproduced, the paid list-price equivalent, and actual spend ($0.00) |
| H3 | Gate precision | When Repro says "reproduced" without seeing the fix, how often it is right |
| H4 | Flaky rate | Share of emitted tests whose outcome changes across 10 reruns |
| H5 | Mutation score | Share of small mutations to the fixed lines that Repro's test catches, next to the human-written tests' score on the same mutations |

README headline sentence (filled by `repro report`, never by hand):

> On free-tier models at $0, Repro reproduces **S%** (95% CI a to b) of 50 real bugs from SWT-bench Verified using a median **T** tokens per bug, against **S0%** for a single prompt with the same model. When it says "reproduced", it is right **P%** of the time. **F%** of its tests are flaky. Its tests kill **M%** of mutants in the fixed lines (human-written tests: **G%**). On a paid tier the same run would have cost about **$C** per bug.

## 2. Data

| Set | What | Size | Used for |
|---|---|---|---|
| Fixtures | Toy repos with a seeded bug, a fix, an issue text, committed in `tests/fixtures/mini_repos/` | 8 | Building and testing the pipeline with no Docker and no API |
| Pilot | Verified instances used only with gold tests (no model runs) | 10 | Checking my oracle against the official harness |
| Dev | SWT-bench Verified instances not in Test | 15 | All prompt, gate, and budget tuning |
| Test | SWT-bench Verified, seeded random sample stratified by repo | 50 | Final numbers. Run once per config. |
| Test-20 | First 20 of Test in the committed order | 20 | Optional cross-model ablation only |

SWT-bench Verified has 433 human-verified instances. Each has an issue, the real fix, and the real tests, derived from SWE-bench Verified.

**Why 50, not 150.** Free-tier quota and free runner time. Tokens are not the limit (section 5); runner-minutes and wall clock are. The cost is precision: about ±13 points at 50 instead of ±8 at 150. Section 4 states exactly what that allows us to claim.

**Pre-registration.** `eval/samples/dev_15.txt` and `eval/samples/test_50.txt` are generated by a seeded script from the 433 Verified ids (stratified by repo, which is the prefix of each instance id) and committed in M7 **before any model sees a Test instance**. The README links that commit. A unit test asserts the two lists are disjoint and that the seeded script regenerates them exactly. The pilot list may overlap Test, since no model runs on pilots.

**What the agent sees:** issue text (`problem_statement`), the repo at the base commit, the repo's test command. **What it never sees:** the fix, the real tests, the names of the failing tests, later issue comments (`hints_text`), git history after the base commit, the network.

## 3. Configurations

| Config | Description | Failover | Run on |
|---|---|---|---|
| `A-main` | Full agent, primary logical model (chosen in M3), defaults from DESIGN 5.6 | `pinned` | Test (50) |
| `B0-main` | Single prompt, BM25 context, no execution, same model | `pinned` | Test (50) |
| `B1-main` | 5 single-prompt samples, first to pass the online gate, same model | `pinned` | Test (50) |
| `A-main+judge` | `A-main` with the LLM judge in G3 | `pinned` | Test (50) |
| `A-main` reruns 2 and 3 | Variance | `pinned` | Test (50) |
| `A-gemini` (optional) | Full agent on a Gemini Flash model | `pinned` | Test-20, only if AI Studio shows at least about 400 requests/day for that model; otherwise dropped and the README says so |
| `A-chain` | Agent with cross-model failover | `chain` | Dev and demo only. Never reported as a headline number. |

Each agent run yields two scoring modes from the same trace (DESIGN 5.6): **always-emit** (best candidate regardless of gate) and **gated** (only if the online gate passed). No extra calls.

Every config is a YAML file in `eval/configs/`. Its hash, the logical model, the exact model version string, the routes allowed, the git commit, and the date `routes.yaml` was last verified are stored in every result row.

Revision 1 used a Sonnet ablation to show "a stronger model helps". There is no free route to a frontier model, so that ablation is gone. The optional `A-gemini` run is the only cross-model comparison.

## 4. Metric definitions

Per instance, every test in the files touched by the candidate gets a transition from the oracle: state on buggy code → state on fixed code.

**Instance outcomes** (exactly one per instance per mode):

| Outcome | Condition |
|---|---|
| REPRODUCED | A test was emitted, at least one F→P, and no test in the touched files fails after the fix |
| WRONG_TEST | A test was emitted but the condition above does not hold |
| NO_TEST | Nothing emitted (abstained, or budget ran out with no candidate; in gated mode also "gate did not pass") |
| INFRA_ERROR | Sandbox or harness failure after one automatic retry, or a unit deferred 3 times |

`DEFERRED` is not an outcome. A deferred unit has no row and runs again later. A run is complete only when every unit has a row.

This matches the SWT-bench success definition: at least one test fails before the fix and all pass after.

### H1. Success rate

- `S = REPRODUCED / N`, with N = all instances in the set. NO_TEST and INFRA_ERROR count as failures. Nothing is dropped from the denominator.
- Reported for always-emit (comparable to published SWT-bench numbers) and gated.
- **Source of truth for always-emit S:** the official SWT-bench harness in unit-test mode, run on exported predictions, for every instance it can score on a free runner. My own oracle computes the same quantity for all 50. If the official harness cannot score some instances (RISKS R12), the README reports both numbers, lists the unscored instances, and uses my oracle's S for the headline.
- **Uncertainty:** Wilson 95% interval. At N=50 and S near 50% that is about ±13 points (25 of 50 gives 37% to 63%).
- **Agent vs baseline:** paired on the same instances and the same model, exact McNemar test. Report both discordant counts (agent-only wins, baseline-only wins) and the p-value.
- **What N=50 can and cannot show:** with 50 pairs, about the smallest result that reaches p < 0.05 is 10 agent-only wins against 2 baseline-only wins (p = 0.039), a net gap of 8 bugs (16 points). 9 against 2 gives p = 0.065. So smaller real gaps will likely read as "not significant", and the README says that rather than claiming a difference. No per-repo success rates are reported (too few instances per repo); only counts.
- Also reported from the official harness: W (patch applies), F→P rate, P→P rate, and change coverage ΔC (share of fix-changed lines the test executes). Reference from the SWT-bench README: the gold tests reach ΔC of 69.1 on Verified.

### H2. Compute

All from the token ledger.

- **Tokens per bug:** in, out, total. Mean, median, p90, max.
- **Requests per bug** and **rate-limit wait per bug** (seconds spent waiting on limiters or retry backoff).
- **Tokens per reproduced bug** = total tokens / REPRODUCED. The product number: what one usable test takes, including every failed attempt.
- **List-price equivalent** = tokens × the paid list price of the same model from `list_prices.yaml` (date stated). Reported per bug and per reproduced bug. A reader can see what it would cost a team on a paid tier.
- **Actual spend:** $0.00, stated as a number, plus runner-minutes used.
- **Route mix:** share of calls served by each route, retries, failovers, circuit-breaker trips, deferrals. For `pinned` configs, cross-model failovers must be 0.
- Invariants, tested: `max(per-instance tokens) <= per-bug ceiling` and `total <= run ceiling`.
- **Token ceiling curve:** S recomputed as if the per-bug ceiling were 50K, 100K, 200K, 400K, 600K tokens, using the per-step token counts in the traces. Shows where extra compute stops paying.

### H3. Gate precision (the product's trust number)

Uses gated mode. "Claimed" = instances where the online gate passed and a test was emitted.

- `precision = REPRODUCED_gated / claimed`, with a Wilson interval (claimed may be around 20 to 30 instances, so the interval will be wide; it is shown, not hidden)
- `recall = REPRODUCED_gated / N` (this is gated S)
- `gate_recall_cost = S_always_emit - S_gated` (reproductions thrown away by the gate)
- `abstain_rate = NO_TEST_gated / N`
- Without-gate comparison: `precision_no_gate = REPRODUCED_always / emitted_always`. The gap between the two precisions is what the gate buys.
- Per-check rejection counts (how many candidates G0 to G5 each rejected) and, for WRONG_TEST cases that passed the gate, a hand-labelled reason.
- Same numbers for `A-main+judge` to price the LLM judge: precision gained per extra 1K tokens.

### H4. Flaky rate

Two different things, reported separately.

1. **In-loop catches.** Candidates rejected by G4 (3 runs, hash seeds 0 to 2, fresh sandboxes). Count and share of all `check` calls. Shows the mechanism fires.
2. **Audit flaky rate.** After the run, every emitted test (gated mode) is run 10 times on buggy code and 10 times on fixed code, fresh sandbox each, hash seeds 0 to 9. A test is flaky if its outcome is not identical across the 10 runs in either state. `flaky_rate = flaky / emitted`.
3. **Control.** The gold tests get the same 10x audit. An instance whose gold tests are flaky is an unstable environment, not a flaky Repro test, and is reported in its own row.

Detection power, stated so the number is not oversold. Probability of catching a test that flips with probability p per run:

| p (flip rate) | 3 runs | 10 runs |
|---|---|---|
| 0.5 | 75% | 99.8% |
| 0.1 | 27% | 65% |
| 0.05 | 14% | 40% |

So "0% flaky" means "no test with a flip rate above roughly 10% is likely to have slipped through", not "no flaky tests". With only about 20 to 30 emitted tests, one flaky test is already 3 to 5%.

### H5. Mutation score

Computed on instances that are REPRODUCED by Repro (the gold tests reproduce every instance by construction).

- Mutants: generated on the fixed code, only on lines changed by the real fix (procedure in DESIGN 5.8), max 30 per instance, seeded.
- `mutation_score = killed / valid_mutants`, per instance; report the mean and median across instances.
- Reference: the gold fail-to-pass tests on the same mutants. Report `score_repro`, `score_gold`, and the paired difference with a bootstrap 95% CI.
- Same for `B0-main` on the instances it reproduced.
- Caveat written next to the number: it only covers the fix-changed lines, equivalent mutants are not removed (they hit both sides of the paired comparison equally), and at this sample size it rests on about 15 to 25 instances.

## 5. Procedure

All runs marked (Actions) are GitHub Actions workflows, started from a chat session through the REST API or by me with `gh workflow run`. Every run is resumable: rerunning the same command continues where it stopped.

| Step | When | What |
|---|---|---|
| P1 | M4 | Metrics code is written and tested against a synthetic `results.jsonl` with known answers |
| P2 (Actions) | E0 | `bootstrap.yml`: install the SWT-bench harness, validate one gold instance, export the 433 Verified ids, record disk and time used |
| P3 (Actions) | M6/E1 | Gold agreement: for the 10 pilot instances, my oracle on the gold tests gives F→P, and the official harness agrees |
| P4 | M7 | Generate and commit `dev_15.txt` and `test_50.txt` (pre-registration commit) |
| P5 (Actions) | M7/E2 | Iterate on Dev only, at most 3 rounds. Every Dev run is stored with its config hash. |
| P6 | M7 | Freeze: tag `eval-freeze-v1`. Prompts, gate rules, budgets, model IDs, and routes do not change after this tag. |
| P7 (Actions) | M9/E3 | Run all Test configs in nightly batches until `repro status` shows every unit has a row. Never rerun a unit that finished. |
| P8 (Actions) | M9/E3 | Export predictions, run the official SWT-bench harness, run the 10x audit, run mutation scoring (no model calls) |
| P9 (Actions) | M9/E3 | Variance: two more full `A-main` runs on Test. Report the spread of S across the 3 runs. |
| P10 | M9 | `repro report --check`. Hand-read 15 failures and label them (section 8). |

**Batch mechanics.** Default batch: 6 shards, each with a 330-minute deadline (inside the 6-hour Actions job limit), `--stop-when-exhausted`. Each finished unit is committed to the `results` branch immediately. A night that ends early (quota out, job killed) just means the next night picks up the rest.

**Estimated volume** (to be replaced by measured numbers in the README):

| Phase | Units | Tokens | Runner-minutes | Nights |
|---|---|---|---|---|
| Dev, 3 rounds | 135 | about 20M | about 2,200 | about 3 |
| Final configs + judge | 200 | about 36M | about 3,600 | about 2 |
| Variance reruns | 100 | about 25M | about 2,300 | about 1 to 2 |
| Audit, mutation, official scoring | n/a | 0 | about 2,800 | about 1 to 2 |

Tokens total about 80M against Mistral's 1B per month, so tokens are not the limit. The binding limit is Mistral's 500K tokens/min, which caps parallelism at about 6 shards. That and runner time set the pace.

**Model decision rule (applied on Dev before the freeze):** if `A-main` always-emit S on Dev is below 3 of 15 after two rounds of prompt iteration, switch the primary to the next model in the preference list (DESIGN 5.5) that Mistral's free mode offers, and restart Dev. The switch and the reason are recorded in `DECISIONS.md`. If no free model clears the floor, the project still reports its numbers; a low S on a free model is a result, and the gate precision and harness work stand on their own.

**If the freeze has to be broken** (a harness bug found during the Test run): fix it, bump to `eval-freeze-v2`, rerun everything affected, and say so in the README. Prompt or gate tuning after seeing Test results is not allowed under any tag.

**If a provider changes its free tier mid-run:** units already finished stand. If the primary model disappears or its limits collapse, the run stops, the change is recorded in `DECISIONS.md`, and the Test run restarts from zero on the next model. Results from two models are never mixed in one table.

## 6. Checks on the eval itself

| Check | Pass condition |
|---|---|
| Gold agreement | On the 10 pilot instances and then on all 50 Test instances, my oracle marks the gold tests F→P. Any exception is listed and excluded up front with a reason. |
| Harness agreement | REPRODUCED from my oracle vs the official harness on always-emit predictions, over every instance the official harness scored: report the agreement rate and list every disagreement. Target: at least 95% (at most 2 disagreements in 50). |
| Model purity | Every headline row has `mixed = false` and the config's single logical model; zero cross-model failovers in `pinned` configs |
| Completeness | Every (instance, config) unit has exactly one row; no unit has more than 3 deferrals without being INFRA_ERROR |
| Leak canary | No fix hunk, gold test body, or fail-to-pass test name appears in any prompt or trace (automated scan over all traces) |
| Memorisation check | Similarity of each generated test to the gold test (normalised token overlap on added lines). Report the share above 0.8 and S with those instances removed. |
| Budget invariants | No instance over its token ceiling; total under the run ceiling |
| Determinism of scoring | Re-running `repro report` on the same results gives a byte-identical table |

| Point | Status |

## 8. Failure notes (required, not optional)

After P8, hand-read 15 non-reproduced Test instances from `A-main` (seeded random pick, not cherry-picked) and label each with one of:

- could not find the relevant code
- reproduced the wrong behaviour (misread the issue)
- test fails for the wrong reason and the gate passed it (gate miss)
- right idea, gate rejected it (gate false reject)
- test placement or runner problem (wrong file, wrong framework conventions)
- ran out of token or step budget while converging
- lost track after context trimming (repeated work, forgot an earlier finding)
- slowed by rate limits until the 60-minute hard cap ran out
- issue needs something the sandbox does not have (network, GPU, external service)
- infra error

The table of counts and two or three specific examples go in the README under "Where it fails". Separately, list every WRONG_TEST that passed the gate, since those are the cases that would embarrass the product.

| Target | Value |
|---|---|
| `A-main` beats `B0-main` | McNemar p < 0.05 |
| `A-main` always-emit S on Test | at least 35% (floor 20%, see decision rule) |
| Gate precision | at least 85% |
| Audit flaky rate | at most 2% |
| Median tokens per bug (`A-main`) | at most 300K |
| Mutation score gap to gold tests | within 15 points |
| Harness agreement | at least 95% |

These are goals, not forecasts. Missing one is a result to explain, not a number to adjust.

## 10. Output files

```
results branch:
  results/<run_id>/
    config.yaml            frozen copy of the config
    shard-<k>.jsonl        result rows, one per unit (merged by `repro report`)
    traces/<instance>.jsonl
    candidates/<instance>.diff
    ledger-<k>.jsonl       every model call with route and tokens
    quota-<k>.json         quota state at the end of each batch
    predictions.jsonl      SWT-bench format
    official_report.json   output of the SWT-bench harness
    audit.jsonl            10x flaky audit
    mutation.jsonl         per-mutant outcomes
    report.md, plots/      generated
```

Final results are merged into `main` in M9. Traces go to `main` if they fit; otherwise they are attached to a GitHub release.
