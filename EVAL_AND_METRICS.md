# Repro: Eval and Metrics

The eval is built before the agent. Milestones M1 to M4 produce the full measuring pipeline on toy bugs; the agent arrives in M5 and is measured from its first run.

Rule for this doc: every number that will appear in the README has a definition, a denominator, and a procedure here. If it is not defined here, it does not go in the README.

## 1. Headline numbers

| ID | Number | One-line definition |
|---|---|---|
| H1 | Success rate S | Share of bugs where Repro's test fails before the real fix and passes after |
| H2 | Cost per bug | LLM dollars per bug attempted, and per bug reproduced |
| H3 | Gate precision | When Repro says "reproduced" without seeing the fix, how often it is right |
| H4 | Flaky rate | Share of emitted tests whose outcome changes across 10 reruns |
| H5 | Mutation score | Share of small mutations to the fixed lines that Repro's test catches, next to the human-written tests' score on the same mutations |

README headline sentence (filled by `repro report`, never by hand):

> Repro reproduces **S%** (95% CI a to b) of 150 real bugs from SWT-bench Verified at a median **$C** per bug, against **S0%** for a single prompt with the same model. When it says "reproduced", it is right **P%** of the time. **F%** of its tests are flaky. Its tests kill **M%** of mutants in the fixed lines (human-written tests: **G%**).

## 2. Data

| Set | What | Size | Used for |
|---|---|---|---|
| Fixtures | Toy repos with a seeded bug, a fix, an issue text, committed in `tests/fixtures/mini_repos/` | 8 | Building and testing the pipeline with no Docker and no API |
| Dev | SWT-bench Verified instances not in Test | 30 | All prompt, gate, and budget tuning |
| Test | SWT-bench Verified, seeded random sample stratified by repo | 150 | Final numbers. Run once per config. |
| Test-50 | First 50 of Test in the committed order | 50 | Model ablation, variance reruns |

SWT-bench Verified has 433 human-verified instances. Each has an issue, the real fix, and the real tests, derived from SWE-bench Verified.

**Pre-registration.** `eval/samples/dev_30.txt` and `eval/samples/test_150.txt` are generated by a seeded script from the 433 Verified ids (stratified by repo, which is the prefix of each instance id) and committed in M7 **before any model sees a Test instance**. The README links that commit. A unit test asserts the two lists are disjoint and that the seeded script regenerates them exactly.

**What the agent sees:** issue text (`problem_statement`), the repo at the base commit, the repo's test command. **What it never sees:** the fix, the real tests, the names of the failing tests, later issue comments (`hints_text`), git history after the base commit, the network.

## 3. Configurations

| Config | Description | Run on |
|---|---|---|
| `A-haiku` | Full agent, Haiku 5.5, defaults from DESIGN 5.6 | Test (150) |
| `B0-haiku` | Single prompt, BM25 context, no execution | Test (150) |
| `B1-haiku` | 5 single-prompt samples, first to pass the online gate | Test (150) |
| `A-sonnet` | Full agent, Sonnet 5.5, $2 per-bug ceiling | Test-50 |
| `B0-sonnet` | Single prompt, Sonnet 5.5 | Test-50 |
| `A-haiku+judge` | `A-haiku` with the LLM judge in G3 | Test-50 |

Each agent run yields two scoring modes from the same trace (DESIGN 5.6): **always-emit** (best candidate regardless of gate) and **gated** (only if the online gate passed). No extra spend.

Every config is a YAML file in `eval/configs/`. Its hash, the exact model ID, the git commit, and the pricing file's `verified_on` date are stored in every result row.

## 4. Metric definitions

Per instance, every test in the files touched by the candidate gets a transition from the oracle: state on buggy code → state on fixed code.

**Instance outcomes** (exactly one per instance per mode):

| Outcome | Condition |
|---|---|
| REPRODUCED | A test was emitted, at least one F→P, and no test in the touched files fails after the fix |
| WRONG_TEST | A test was emitted but the condition above does not hold |
| NO_TEST | Nothing emitted (abstained, or budget ran out with no candidate; in gated mode also "gate did not pass") |
| INFRA_ERROR | Sandbox or harness failure after one automatic retry |

This matches the SWT-bench success definition: at least one test fails before the fix and all pass after.

### H1. Success rate

- `S = REPRODUCED / N`, with N = all instances in the set. NO_TEST and INFRA_ERROR count as failures. Nothing is dropped from the denominator.
- Reported for always-emit (comparable to published SWT-bench numbers) and gated.
- **Source of truth for the always-emit S is the official SWT-bench harness in unit-test mode**, run on exported predictions. My own oracle computes the same quantity; the two must agree (section 6).
- Uncertainty: Wilson 95% interval. At N=150 and S near 50% that is about plus or minus 8 points; at N=50 about plus or minus 13.
- Agent vs baseline: paired on the same instances, exact McNemar test. Report both discordant counts (agent-only wins, baseline-only wins) and the p-value.
- Also reported from the official harness: W (patch applies), F→P rate, P→P rate, and change coverage ΔC (share of fix-changed lines the test executes). Reference from the SWT-bench README: the gold tests reach ΔC of 69.1 on Verified.

### H2. Cost

All from the ledger. LLM cost only; VM cost is reported separately as hours times hourly rate.

- `cost_per_bug_mean = total_cost / N` and the median, p90, and max per instance.
- `cost_per_reproduced_bug = total_cost / REPRODUCED`. This is the product number: what one usable test costs, including all the failed attempts.
- Also: tokens in and out, steps, gate checks, wall clock per instance (median, p90).
- Invariant, tested: `max(per-instance cost) <= per-bug ceiling` and `total <= run cap`.
- Cost vs success curve: S recomputed as if the per-bug ceiling were $0.02, $0.05, $0.10, $0.25, using the step timestamps and costs in the traces. Shows where extra spend stops paying.

### H3. Gate precision (the product's trust number)

Uses gated mode. "Claimed" = instances where the online gate passed and a test was emitted.

- `precision = REPRODUCED_gated / claimed`
- `recall = REPRODUCED_gated / N` (this is gated S)
- `gate_recall_cost = S_always_emit - S_gated` (reproductions thrown away by the gate)
- `abstain_rate = NO_TEST_gated / N`
- Without-gate comparison: `precision_no_gate = REPRODUCED_always / emitted_always`. The gap between the two precisions is what the gate buys.
- Per-check rejection counts (how many candidates G0 to G5 each rejected) and, for WRONG_TEST cases that passed the gate, a hand-labelled reason.
- Same numbers for `A-haiku+judge` on Test-50 to price the LLM judge: precision gained per extra dollar.

### H4. Flaky rate

Two different things, reported separately.

1. **In-loop catches.** Candidates rejected by G4 (3 runs, hash seeds 0 to 2, fresh sandboxes). Count and share of all `check` calls. Shows the mechanism fires.
2. **Audit flaky rate.** After the run, every emitted test (gated mode) is run 10 times on buggy code and 10 times on fixed code, fresh sandbox each, hash seeds 0 to 9. A test is flaky if its outcome is not identical across the 10 runs in either state. `flaky_rate = flaky / emitted`.
3. **Control.** The gold tests get the same 10x audit. An instance whose gold tests are flaky is an unstable environment, not a flaky Repro test, and is reported in its own row.

Detection power, stated so the number is not oversold. Probability of catching a test that flips with probability p per run:

| p (flip rate) | 3 runs | 10 runs |
|---|---|---|
| 0.5 | 75% | 99.8% |
| 0.1 | 27% | 65% |
| 0.05 | 14% | 40% |

So "0% flaky" means "no test with a flip rate above roughly 10% is likely to have slipped through", not "no flaky tests".

### H5. Mutation score

Computed on instances that are REPRODUCED by both Repro and (trivially) the gold tests.

- Mutants: generated on the fixed code, only on lines changed by the real fix (procedure in DESIGN 5.8), max 30 per instance, seeded.
- `mutation_score = killed / valid_mutants`, per instance; report the mean and median across instances.
- Reference: the gold fail-to-pass tests on the same mutants. Report `score_repro`, `score_gold`, and the paired difference with a bootstrap 95% CI.
- Same for `B0-haiku` on the instances it reproduced.
- Caveat written next to the number: it only covers the fix-changed lines, and equivalent mutants are not removed (they hit both sides of the paired comparison equally).

## 5. Procedure

Steps marked (box) run on the eval box. Everything else runs anywhere.

| Step | When | What |
|---|---|---|
| P1 | M4 | Metrics code is written and tested against a synthetic `results.jsonl` with known answers |
| P2 (box) | E0 | Install the SWT-bench harness, validate one gold instance |
| P3 (box) | M6/E1 | Gold agreement: for 10 pilot instances, my oracle on the gold tests gives F→P, and the official harness agrees |
| P4 | M7 | Generate and commit `dev_30.txt` and `test_150.txt` (pre-registration commit) |
| P5 (box) | M7/E2 | Iterate on Dev only. Every Dev run is logged in `eval/results/dev/` with its config hash. |
| P6 | M7 | Freeze: tag `eval-freeze-v1`. Prompts, gate rules, budgets, and model IDs do not change after this tag. |
| P7 (box) | M9/E3 | Run all Test configs once. Resume on crash; never rerun an instance that finished. |
| P8 (box) | M9/E3 | Export predictions, run the official SWT-bench harness, run the 10x audit, run mutation scoring |
| P9 (box) | M9/E3 | Variance: rerun `A-haiku` twice more on Test-50. Report the spread of S across the 3 runs. |
| P10 | M9 | `repro report`. Hand-read 20 failures and label them (section 8). |

**Model decision rule (applied on Dev before the freeze):** if `A-haiku` always-emit S on Dev is below 35% after two rounds of prompt iteration, switch the primary config to Sonnet 5.5 and shrink Test to the first 100 instances of the committed order to stay inside the budget. The switch and the reason are recorded in `DECISIONS.md`.

**If the freeze has to be broken** (a harness bug found during the Test run): fix it, bump to `eval-freeze-v2`, rerun everything affected, and say so in the README. Prompt or gate tuning after seeing Test results is not allowed under any tag.

## 6. Checks on the eval itself

| Check | Pass condition |
|---|---|
| Gold agreement | On the 10 pilot instances and then on all 150 Test instances, my oracle marks the gold tests F→P. Any exception is listed and excluded up front with a reason. |
| Harness agreement | REPRODUCED from my oracle vs the official harness on always-emit predictions: report the agreement rate and list every disagreement. The official result is what gets published. Target: at least 97% agreement. |
| Leak canary | No fix hunk, gold test body, or fail-to-pass test name appears in any prompt or trace (automated scan over all traces). |
| Memorisation check | Similarity of each generated test to the gold test (normalised token overlap on added lines). Report the share above 0.8 and S with those instances removed. |
| Budget invariants | No instance over its ceiling; total under the cap. |
| Determinism of scoring | Re-running `repro report` on the same `results.jsonl` gives a byte-identical table. |

How Repro's numbers may and may not be compared to these:

| Point | Status |
|---|---|
| Same benchmark and same scoring harness | Yes |
| Same instances | No. Repro uses a 150-instance random sample; published numbers use all 433. Compare using the CI. |
| Same model | No. State the model next to every number. |
| Verified by the maintainers | No. Repro is self-run. |
| Same mode | Repro is unit-test mode. Some leaderboard entries use reproduction-script mode, which is a different and easier task. |
| My B0 vs published Zero-Shot Plus | Same idea (single prompt, BM25, about 27K tokens of context), my own implementation, newer model. A reference point, not a controlled comparison. |

Nothing in the README may say or imply a leaderboard rank. Stretch: if budget is left, run the full 433 and submit to the leaderboard for a verified number.

## 8. Failure notes (required, not optional)

After P8, hand-read 20 non-reproduced Test instances from `A-haiku` (seeded random pick, not cherry-picked) and label each with one of:

- could not find the relevant code
- reproduced the wrong behaviour (misread the issue)
- test fails for the wrong reason and the gate passed it (gate miss)
- right idea, gate rejected it (gate false reject)
- test placement or runner problem (wrong file, wrong framework conventions)
- ran out of budget while converging
- issue needs something the sandbox does not have (network, GPU, external service)
- infra error

The table of counts and two or three specific examples go in the README under "Where it fails". Separately, list every WRONG_TEST that passed the gate, since those are the cases that would embarrass the product.

## 9. Targets (set now, reported as hit or miss)

| Target | Value |
|---|---|
| `A-haiku` beats `B0-haiku` | McNemar p < 0.05 |
| `A-haiku` always-emit S on Test | at least 50% (floor 35%, see decision rule) |
| Gate precision | at least 85% |
| Audit flaky rate | at most 2% |
| Median cost per bug | at most $0.10 |
| Mutation score gap to gold tests | within 15 points |
| Harness agreement | at least 97% |

These are goals, not forecasts. Missing one is a result to explain, not a number to adjust.

## 10. Output files

```
eval/results/<run_id>/
  config.yaml            frozen copy of the config
  results.jsonl          one row per instance per config (schema in DESIGN section 6)
  traces/<instance>.jsonl
  candidates/<instance>.diff
  predictions.jsonl      SWT-bench format
  official_report.json   output of the SWT-bench harness
  audit.jsonl            10x flaky audit
  mutation.jsonl         per-mutant outcomes
  ledger.jsonl           every LLM call with cost
  report.md, plots/      generated
```

Result files for the final run are committed to the repo. Traces are committed if they fit; otherwise attached to a GitHub release.
